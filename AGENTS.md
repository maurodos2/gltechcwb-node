# AGENTS.md

E-commerce `gltechcwb` — Express + MongoDB (Mongoose) + EJS. Storefront pt-BR: loja pública, painel admin, checkout com Mercado Pago (Pix/cartão). **Não há testes, lint nem typecheck** — validação é rodar o servidor e exercitar as rotas.

## Comandos

- `npm run dev` — nodemon em `server.js` (porta 3000).
- `npm run seed` — cria o 1º admin a partir de `SEED_ADMIN_EMAIL/PASSWORD` do `.env` (idempotente). Necessário antes de `/admin` fazer login.
- `npm run import-catalog -- migracao/categorias.json migracao/produtos.json` — upsert idempotente de catálogo por `slug` (categoria) e `sku` (produto). Hardcoda `type: 'produto'`.
- `npm run import-manufacturer -- SKU [SKU...]` — ferramenta manual: pesquisa o site oficial do fabricante, baixa imagens (para o R2) e descrição (só se vazia). Mesma engine do painel `/admin/imports`. Pode repetir sem duplicar.
- `npm run remove-services` — apaga todos os `type: 'servico'` e a categoria "Serviços Técnicos". Rodar para limpar serviços.
- `npm run build:assets` — minifica `public/js/*.js` e `public/css/*.css` (terser + clean-css) gerando `public/dist/*.min.*` + `manifest.json`. As views usam `asset('/css/site.css')` (helper em `server.js` app.locals) que troca para o `.min` quando `NODE_ENV=production`. Rodar após alterar JS/CSS do site público e incluir `public/dist/` no deploy.

Ordem típica de setup local: `npm install` → copiar `.env.example` para `.env` → `npm run seed` → `npm run import-catalog -- migracao/categorias.json migracao/produtos.json`.

## Ambiente

- `.env` obrigatório (`config/db.js` faz `process.exit(1)` sem `MONGO_URI`). O `.env` real aponta para o Atlas e contém segredos; `.env` e `atlas-credentials.env` são gitignored — nunca commitar, logar ou exibir seus valores.
- `SEED_ADMIN_*` só são usados pelo seed. `WEBHOOK_SECRET` está em `.env.example`/`render.yaml` mas **não é validado** em código.
- Node 20 fixado em `engines` + `render.yaml` (fix de compatibilidade TLS com Atlas).

## Convenções

- Tudo voltado ao usuário é **pt-BR**: views, mensagens de log, comentários, README. Manter.
- Formulários HTML usam `method-override` via `?_method=PUT|DELETE` (configurado em `server.js`).
- Helpers globais de view ficam em `app.locals` (em `server.js`): `formatPrice`, `effectivePrice`, `minVariantPrice`, `whatsappUrl`. Não redifinir nas views.
- SEO em `lib/seo.js`: meta descriptions dinâmicas (120–150 chars; nome + preço + CTA "Compre em até 12x"), JSON-LD Product/BreadcrumbList nas PDPs e WebSite + ElectronicsStore + ItemList na home. Rotas em `routes/shop.js` passam `metaDescription`/`ldJson`/`crumbsJson`/`ldHomeJson`; `standardDescriptionHtml` monta o template padrão (Ficha Técnica, Para quem é, Benefícios, Garantia) quando a descrição do produto é curta. Regenerar metas/JSON-LD é automático da renderização — não precisa de job.
- O middleware que carrega `navCategories` pula paths `/admin` e `/api`.
- Webhooks do Mercado Pago validam assinatura HMAC (`x-signature`) via SDK oficial; `WEBHOOK_SECRET` deve ser o **secret gerado no painel MP** (Suas integrações > Webhooks), não um valor inventado.

## Arquitetura

- `server.js` é o ponto único de montagem: qualquer rota nova precisa ser `app.use(...)` lá.
- `routes/api/*` são a API pública JSON; `routes/admin/*` são protegidos por `requireAdminAuth` (exceto `auth.js`, montado antes do guard); `requirements` de cliente usam `requireCustomerAuth`.
- `lib/` tem `mail.js` (e-mail transacional: **Resend** por API HTTPS quando `RESEND_API_KEY` existe — usado em produção — e fallback SMTP Zoho para dev) e `storage.js` (upload de imagens no Cloudflare R2 via S3 SDK; `R2_*` no `.env`, upload em memória no admin). Mercado Pago e frete estão embutidos em `routes/checkout.js` e `routes/api/shipping.js`.
- Frete usa ViaCEP + tabela simulada (não é a API dos Correios ainda).
- Imagens de produto: `Product.images` guarda URLs completas do R2 (`R2_PUBLIC_BASE_URL/produtos/...`); `public/uploads` não é mais usado para novos uploads.
- `migracao/` contém scripts Python que **geram** `categorias.json`/`produtos.json`; não editar os JSONs como fonte.
- `connect-mongo@6` exige a linha de interop no topo de `server.js` (`require('connect-mongo').default || require('connect-mongo')`) — não mexer.
- Model `Product`: `type` só aceita `'produto'` (serviços foram removidos); suporta `variants`, `promoPrice`, `hasVariants`, `barcode`, `specs`, texto-search indexado.

## Backlog / Pendências

- **CSRF origin check:** reativado e **validado**. `BLOCK_CROSS_ORIGIN = true` em `server.js` desde 2026-09-15, após consulta ao Mongo confirmar **0 eventos cross-origin em `security_events`** em ~1 semana pós-migração OCI. Validação feita via curl `-H "Origin: evil"` em POST → **403** (e GET normal → 200; GET é protegido por `SameSite=Lax`, o middleware cobre apenas POST/PUT/DELETE/PATCH). A lógica tolera `www`/subdomínio/proxy reescritor de Host. `security_events` só grava em `NODE_ENV=production`.
- **Shop de fabricantes:** ferramenta **manual** implementada (botão em `/admin/imports` + `npm run import-manufacturer`, com `--modelo "X"` para produto sem código no nome) com os importadores **TP-Link** (scraping do site oficial; live) e **Intelbras** (API pública da loja VTEX `intelbras.vtexcommercestable.com.br/api/catalog_system/pub/products/search` + fallback no site institucional via `sitemap.xml`, para produtos fora da loja/descontinuados — foto oficial sem descrição) e **Logitech** (`sitemap.xml` resolve o slug do produto pelo modelo; página pt-BR espelhada via hreflang com `og:description` em português + fotos originais em `resource.logitech.com` sem o prefixo de transform — `og:image` global é ignorada) e **memória/SSD** (ADATA: fotos oficiais no JSON da página Next.js em `webapi3.adata.com`; Patriot: foto oficial no `og:image` do CDN `patriot-cms-media...`) e **Intel** (`lib/manufacturer/intel.js`: processadores boxed; fonte principal **Pauta Distribuidora** — `pauta.com.br`, de quem a loja compra — que publica as fotos oficiais da caixa; modelos que o site público da Pauta não lista, ex. o i3-12100F, usam a foto oficial espelhada por revendedor "Intel Oficial" (gigantec). Extensible: tabela `FONTES` por modelo). **Kingston e WD Green** passaram a ter importador em 2026-09-16 via `lib/manufacturer/gigantec-mirror.js` (revenda autorizada **gigantec.com.br** — o mesmo host das fotos Intel — pois os sites oficiais bloqueiam: `kingston.com` responde 403 anti-bot e `westerndigital.com` 404 para a linha WD Green descontinuada): FONTES estática por modelo (`kvr32n22s8`, `kvr32n22s8l`, `a400`, `sa400s37`, `wds480g3g0a`) com URLs `media/catalog/product/...` achadas na busca da própria gigantec (200 e foto confirmada 206 image/jpeg); fotos subidas no R2 e `manufacturerRef` gravado para AEM-0003/0007/0008/0009. **Sem importador** (informado no relatório e SEM fonte HTTP-viável): **Crucial** (`crucial.com` só expõe fotos por JS; a busca gigantec não devolve o modelo CT8G4SFRA266) e **Memória Kingston DDR3 KVR1333D3N9** (não listada no gigantec). Áudio: **Oneal** (foto oficial do produto nas listagens; modelos descontinuados OB-408/OB-1315R têm só a foto da listagem, sem descrição) e **Kadosh** (WooCommerce oficial da Kadosh Music; sitemap resolve slug por modelo; `og:image` + `og:description` pt-BR; CDN Hostinger responde 429 quando o IP excede rajada de requisições — o importador espera ~6s entre pedidos e faz backoff no 429). `Product.manufacturerRef` guarda modelo/URL/fonte. Para novas marcas: criar importador em `lib/manufacturer/<marca>.js` implementando o contrato `obter(modelo)` → `{ url, nome, descricao, imagemPrincipal, galeria, filtrarPorModelo }` + exportar `HOSTS_IMAGENS`; registrar em `lib/manufacturer/import.js` (`IMPORTADORES`) e, se preciso, estender `detectarMarca`/`extrairModelo`. Decisão de design: dados vindos de fontes oficiais acessíveis via HTTP — TP-Link aceita busca por modelo; Intelbras é via API VTEX (busca no site é JS).

- **Bot de atendimento WhatsApp:** ferramenta via `whatsapp-web.js` (QR code, sessão persistente em `.wwebjs_auth/`). Ativada com `WHATSAPP_BOT_ENABLED=true` no `.env`. Fluxos: FAQ por palavras-chave/teclado numérico (1-6), rastreio de pedido pelo número do WhatsApp, busca no catálogo (com envio da foto) e handoff (para grupo via `WHATSAPP_HANDOFF_GROUP`). Quando `human`, o bot fica mudo e repassa mensagens ao grupo de suporte; "oi/menu" volta ao modo automático. **Mudança 2026-09-21:** o handoff é **permanente** — depois da opção 6 (ou intent "atendente") o bot não volta sozinho ao menu/FAQ; toda mensagem do cliente é repassada ao grupo (`msg.fromMe` é ignorada para não ecoar resposta do atendente). O caminho admin para reativar o bot é o botão **"Voltar conversas em modo humano ao bot"** em `/admin/whatsapp` (`POST /admin/whatsapp/reset`, flips `status: 'human'` → `'bot'`). **Menu por extenso:** "opção 6" / "opção número seis" também acionam a opção do menu (regex `opc(?:ao|oes) ...` mapeando `seis`→6 etc., em `bot.js` e no guard do n8n); e o regex de `horario` usa `atendiment` (não `atend`) para não engolir "atendente" — precedência de intenção corrigida. **Bridge n8n (cérebro):** com `WHATSAPP_N8N_WEBHOOK` + `WHATSAPP_N8N_KEY` no `.env`, o bot vira transporte e toda mensagem é decidida pelo workflow **"WhatsApp WA Bridge"** (n8n OCI, webhook `/webhook/wa-in`, header `x-wa-key` obrigatório — senão 500 na hora; em falha do n8n o bot cai para a lógica local, nunca bloqueia o cliente). Contrato: `{ waId, phone, body, status, context, historico, agora }` → `{ replies:[{texto}|{tipo:'imagem',url,legenda}], handoff, context }`. **Anti-backlog (obrigatório preservar):** ao reconectar, o WhatsApp reprocessa mensagens do período offline — o bot só responde mensagens com `timestamp` recente (`WHATSAPP_MAX_MSG_AGE_SEC`, default 120) e ignora mídia/corpo vazio sem histórico de texto do cliente (`WHATSAPP_COOLDOWN_MS` evita rajada; bug histórico de "disparar pra todo mundo" era o registro de `user` vazio em `bot.js` fora do `if (intent)` + falta dos guards). Painel em `/admin/whatsapp` (restrito ao admin) mostra status, QR e botão de teste. **Dependências novas:** `whatsapp-web.js` + `qrcode-terminal` + `qrcode`. **No Render:** requer Chromium headless (buildpack ou `puppeteer.executablePath`); a sessão é apagada a cada deploy — no dev local com `LocalAuth` persiste. O transport é agnóstico e suporta futura migração para a Cloud API oficial.
## SEO local (NAP) — convenções

- **Ordem de impacto:** Google Business Profile (ficha da loja, `business.google.com`) > NAP consistente > JSON-LD LocalBusiness > conteúdo local > citações/diretórios. O JSON-LD e o rodapé só ajudam **se o GBP existir** com os mesmos dados. NAP = Nome + Endereço + Telefone idênticos em todo lugar (site, GBP, redes, notas/fatura).
- **Dados NAP reais** vivem em env vars (`STORE_ADDRESS_*`, `STORE_OPENING_HOURS`, `CONTACT_PHONE`) com fallback para os valores reais no código: Rua Acyr Guimarães, 195 - Apto 171 · Água Verde, Curitiba/PR, CEP 80240-230 · `+55 41 3030-1240` · seg–sex 08:00–18:00. Para mudar: alterar `.env` (e o fallback em `server.js` mantém NAP consistente) + atualizar o GBP no mesmo dia.
- `lib/seo.js` `homeJsonLd` monta `ElectronicsStore` com `address` completo (streetAddress, postalCode, GeoCoordinates reais de `STORE_ADDRESS_LAT/LNG`) e `openingHoursSpecification` expandido (range `Mo-Fr` é parseado e vira lista de dias por extenso). `routes/shop.js` repassa `storeLocal` via `res.locals`. Rodapé (`site-foot.ejs`) exibe o NAP público.
- **Não inventar coordenadas/endereço**: geocodificar com Nominatim open (`python3 -c` + json, User-Agent próprio) e validar que o `street` do Nominatim bate com o endereço em produção antes de gravar no `.env`.
- **Tracking params** (`srsltid`, `gclid`, `utm_*`, `fbclid`…) são removidos com 301 em `server.js` (middleware antes do trim de barra) — evita URL duplicada no Search Console/inventário do Google quando o usuário chega via Google/redes sociais. Params da loja (`q`, `ordem`, `page`) são preservados.
